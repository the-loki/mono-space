# 平台判断交给 agent，应用侧不再解析

用户决策（本任务唯一目标）：

> 「**平台判断也交给 agent**」

本条是一次**决策反转**：推翻了 ADR-0003 当初「应用侧解析平台、不给 agent 自报平台名的口子」。

## 它推翻了什么

ADR-0003 的「追加：平台逐条判断」定下了平台是**逐条 key** 的属性，但把**判断权**留在应用侧。
`src/main/data/page-ingest.ts` 里有一整套**三层回退**的解析：

1. **兑换链接域名**（`PLATFORM_DOMAINS`：fab.com / epicgames / steampowered / unity / gog）——
   因为词边界匹配不到 `steampowered.com` 这种连写域名；
2. **文章 slug**（`parsePlatform`：从 `…-How-to-Redeem-on-Epic-Games` 这类 slug 里认词）；
3. **资产显示名里的平台词**（`PLATFORM_TOKENS` 正则：fab|epic|steam|unity|gog）。

`keys_ingest` 的输出 schema 里甚至**刻意不给 agent 自报平台名的口子**，只收原始证据
（`redemptionUrl`），由应用解析。

本条把这**三层全部删除**，平台的判断改由 **agent 读页面时直接给出**：
`keys_ingest` 的每条 key 新增 `platform` 字段，agent 逐行判断后交上来。

## 为什么

- **用户要彻底 agent 驱动**：页面结构不确定时的判断归 agent，这是 ADR-0005 已经定过的方向
  （揭示、兑换都交出去了），平台没有理由例外。
- **代码猜平台本质是在替模型判断**：那套正则是把「哪些字串算 Epic」写死。它看起来确定，
  实际是在用代码近似一个语义判断——而页面一改版（域名换、slug 变、资产名改写），它就会
  **悄悄失准**：不报错、不崩，只是把平台记错，正是项目反复要避免的「静默失效」。
- **agent 本来就在读那一行**：它已经在读资产名、揭示状态、兑换链接；多判一个平台是顺手的事。
  代码侧为了同一件事维护三层回退、正则、以及「词边界 vs 连写域名」这类细节，收益并不成立。

## 删掉了什么

- `page-ingest.ts` 的 `PLATFORM_DOMAINS`、`PLATFORM_TOKENS`、`articleNameOf`、`resolvePlatform`、
  `parsePlatform`、`NO_LINK_MARKERS` 及围绕它们的注释（含「为什么单独一层」那类说明）；
- `keys_ingest` 描述里「平台由应用从 redemptionUrl 解析，你不需要（也不要）自己判断平台名」；
- `prompts.ts` / `session.ts` 里同义表述；
- 只测这三层解析的单测。

`redemptionUrl` **保持现状**：它仍是每一行「Redemption Instructions」链接的证据
（兑换时用来判断去哪家商店），只是不再兼任平台解析的输入。

## 代价（明说，不是 bug）

- **agent 可能判错，甚至编造**。代码侧不再有「第二只眼睛」复核语义；唯一的护栏是
  **提示词纪律**（逐行判断、判不出写 `unknown`、不许编）与**事后审计**
  （`keys_ingest` 的写入强制留痕）。这是把判断权交出去必然要付的价钱。
- **覆盖率可能变差**：以前第三层「资产显示名里的平台词」虽然会误判，但确实填上了一些行；
  删掉后那些行还能不能判出平台，完全取决于 agent 读得够不够仔细。
- **代码侧只保留「收敛」**：取值必须是台账既有平台名之一（`fab` / `epic` / `steam` / `unity` /
  `gog` / `unknown`）；缺失 / 空串 / 纯空白 / 无法识别的值**一律落成 `unknown`**。
  代码不判断「对不对」，只保证「合法」。

## 边界：一行判不出，不回滚整单

`platform` 在 `keys_ingest` 的 schema 里是**可选**的自由字符串，**不做非空 / 枚举约束**；
应用侧用 `normalizePlatform` 收敛取值，**绝不抛错**。

这条来自两次真实教训（见 ADR-0003 的「教训」与 ADR-0004）：

- `redemptionUrl` 当年加了 `minLength: 1`，**一行不合格就让整笔落库回滚**，
  「一行没写」被放大成「整单丢失」（68 单丢 10 单，其中 4 单共丢 145 个真实 key）；
- 所以平台也走同一条路：**缺失 / 空串 / 空白 / 无法识别 ⇒ `unknown`，整笔照常写入**。
  一行判不出平台，不该连累订单名、资产包与其它行。

schema 用自由字符串而不是字面量联合，也是同一个理由：联合会让「判不出」的写法在 schema 层
直接报错、一行不合格就拖垮整单。

## 逐行判断，不是「一页一平台」

平台判断必须**逐行**：同一张订单页里可能混排多个平台（同一次订单里 Epic 与 Unity 并存是实测过的）。
所以提示词与工具描述都写明：**每一行看它自己的「Redemption Instructions」链接以及该行文案，
不要假设「一页一平台」**。

## 接口补充行的 platform

ADR-0004 的接口补充行**不是 agent 从页面读来的**，没有它的判断可用，所以继续留 `null`
（＝「从未有过平台判断」，界面按「未知」显示）。**不拿接口的 `machine_name` 后缀猜**——
那是旧「引擎」语义，不是平台；写死 `unknown` 反而会掩盖「这一行没人判过」这个事实。

## 与既有 ADR 的关系

- **ADR-0003**：其「平台逐条判断」的结论（平台是 key 级属性）**保留**；
  其「由应用解析文章 slug / 链接域名 / 资产名」的做法**被本条取代**。
- **ADR-0004**：合并仍是应用侧的确定性逻辑，不受影响；只有「补充行 platform」的解释改准。
- **ADR-0005**：同一个方向——页面上的判断交给 agent。
