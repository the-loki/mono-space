# 接口的 key 只作补充，页面永远优先

用户决策（2026-09-26）：

> 「通过页面获取之后，再通过接口获取一次进行合并」
> 「key 码也合并，但页面优先」

## 修订（2026-09-27）：同码补充行会被吸收

本文早先写「本项目不删除任何行」。用户后来决定：**揭示时吞掉同码的补充行**，并**一并清掉**
库里已有的重复补充行。所以现在**会删**，但只在**一种**情况下：**某个码已被页面行持有**时，
删掉**同一订单内**持有该码的 `api:` 行——它们已被页面行取代。**页面行永不删**。
机制与原因见下方 Consequences 里的「同码补充行的吸收」。与之矛盾的旧结论已在原处改写，
历史正文保留在下方。

## 它推翻了 ADR-0003 的哪一部分

ADR-0003 有一条红线：接口的订单详情响应「带着 key，是接口取码的红线」，因此
**不再请求逐单详情（`?all_tpkds=true`）**，接口只提供订单列表。

本条**重开了这条红线的一半**：

- **推翻**：「接口不得取码」——现在**允许**接口提供 key 码。
- **保留**：「接口只提供订单列表」——**同步管线不动**。`runSync` 仍然全程只发一次
  `GET /api/v1/user/order`，产出的订单只有 gamekey、不建任何 key（测试钉住 `http.calls` 长度为 1）。
  逐单详情只在「页面读完之后」的**合并那一趟**里被请求，且只用来补缺口。

换句话说：取码的**主途径仍是页面**，接口从「禁止提供码」降为「只许补充码」。

## 新边界（硬约束）

- **页面永远优先**：同一条 key 若两边都有，**页面读到的字段为准**；
  接口的码**绝不覆盖**页面的码。这条要有测试钉住。
- **接口的码只作补充**：接口有、页面没有的码 → 补进台账（这是「查缺口」的价值）。
- **合并的连接键是兑换码**。两套身份对不上：页面读来的身份是**资产显示名 slug**
  （`page-ingest.ts` 的 `pageKeyRemoteIds`），接口的身份是 `machine_name#keyindex`。
  既然身份无法相互映射，就只能按**兑换码**对齐（同码即同一条 key）。
- **页面有、接口没有 ⇒ 保留**：包括**未揭示因而没有码**的行，绝不因为接口没有就删。
- **接口那一趟失败不得回退掉页面那份**：页面先落库；接口失败只降级为「没合并」，
  如实记录原因，**不抛**——一次网络抖动不该把已经读好的页面数据判成失败。
- 合并是**应用侧的确定性逻辑**，不交给模型判断（不新增需要 agent 决策的工具）。

## Considered Options

- **维持 ADR-0003，接口完全不许取码**——被否：用户明确要求「再通过接口获取一次进行合并」，
  页面漏读的码需要一个独立来源来查缺口。
- **接口的码与页面的码平权（或接口优先）**——被否：用户明确「页面优先」。
  页面是权威显示面；接口只用来补页面缺的那部分。
- **按名字 / 位置把两边对齐**——被否：页面没有机器名，接口没有页面显示名的权威映射，
  两套身份对不上；强行对齐会给出看起来正确、实际错位的值，比「对不上就只按码对齐」更危险。
- **合并做成 agent 工具，让模型判断**——被否：合并规则是确定的（同码页面赢、独有码补进来），
  没有需要判断的地方；交给模型只会引入不确定性，且「页面优先」就不再由应用保证了。

## Consequences

- **代价 / 已知风险**：接口的码与页面的码若**不一致**（同一个 key 在两边的码不同），
  我们**认不出它们是同一条**（连接键就是码本身），于是接口那个码会作为一条**补充行**新增，
  台账里同时存在两行。我们**选页面**，因此可能记录到与接口不一致的值。
  **这不是 bug，是这条决策的代价**：连接键只能是兑换码，而码不一致就等价于「对不上」。
- **同码补充行的吸收（原「次级风险（重读不删除）」，2026-09-27 修订）**：若某条 key 先被接口补进来
  （阶段一落库时页面还没读到码），之后页面又读到**同一个码**（阶段二揭示写回），页面那条正常更新，
  **旧的 `api:` 补充行会被删除**——它已被页面行取代。触发面只有一个：**页面行**写入兑换码 C 时，
  删掉**同一订单内**持有同一个 C 的 `api:` 行；判据是 `remote_id` 以 `api:` 开头（页面身份永远造不出），
  **只删 `api:` 行，绝不删页面行**；幂等，重复写同一个码删 0 条。
  **为什么要删**：新流程是「一次点击 = 阶段一读页面并落库 + 阶段二逐行揭示并写回」，而合并挂在
  阶段一之后 —— 阶段一落库时那些行还没揭示、页面侧一个码都没有，合并因此按接口把码补成 `api:` 行，
  阶段二揭示后才拿到真码写回页面行，于是**同一个码在库里出现两条**。
  真实数据：全库 **105 条 `api:` 补充行，100% 与某条页面行同码**（来自 Unreal 系资产包）。
  历史重复行由 schema **v4 迁移**一次性清掉；此后由落库层的吸收保证不再长。
- **补充行要有来源标记与稳定身份**：否则无法与页面身份区分、重读还会重复。实现用
  `api:<machine_name>#<keyindex>` 身份（`:` 是页面 slug 永远造不出的字符），并靠身份 + 按码去重保证幂等。
- **补充行不猜平台**：接口的 `machine_name` 后缀是旧「引擎」语义，不拿来猜平台。补充行不是 agent
  从页面读来的，没有它的平台判断可用，所以留 `null`（＝「从未有过平台判断」，界面按「未知」显示）。
  页面行的平台自 **ADR-0006** 起由 agent 逐行给出；本条只管合并，不新增平台来源。
- **落库仍走既有入口**：合并结果依旧是 `SyncedOrder`，经 `repository.applyOrderSync` 落库，
  不另造一条持久化路径。
- **ADR-0003 的历史正文不改**：只在其「追加」区补一句指引，说明部分边界已被本条重开。

证据与实测校准见 `docs/verify/19-v1-acceptance.md`；ADR-0003 里订单页真实 DOM / 身份推导的结论仍有效。
