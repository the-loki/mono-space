   而 CSS 规定不加引号的值必须是合法标识符、**不能以数字开头** —— 恰好那 4 单的订单号以数字开头

   （第一轮成功的那些单，订单号都以字母开头 —— 与这个解释 100% 吻合。）
3. 第二轮（补跑日志 `retry2.log`）跑完 4 单，全库未揭示 48 → 46。

## 3. 为什么码在台账里、页面行却仍标「未揭示」

合并的连接键是**兑换码**（ADR-0004：两套身份对不上，只能用码当连接键）。
页面行**从来没有出现过码**（页面给的是「已过期」或干脆没有密钥栏），于是：
接口给的码落成**新的 `api:` 补充行**，页面行保持「未揭示」 —— 两条记录讲的是同一个资产。

⇒ 这是 ADR-0004 「码当连接键」的**已知代价，现在有了真实数据量**：27 条。
要不要额外用「资产名」把这两行并起来（把码搬到页面行、删掉补充行）是**产品决策**：
按名匹配正是当初为了避开「显示名 vs machine_name 对不上」而放弃的做法，如今它却是唯一的可用信号。

## 4. 顺带发现的**数据口径问题**：「已揭示」不代表「有码」

```
1087 keys = 有码 1002 + 无码 85
                         ├─ 未揭示 46
                         └─ 标记「已揭示」却没有码  39 条（**全是页面行**）
另有 26 条的「码」其实是 URL（Synty 折扣/购物车链接）
```

`reveal_status='revealed'` 现在的实际含义是「**页面上不再有隐藏态**」，**不是**「我们拿到了码」。
于是界面会显示「已揭示」而码列为空。这 39 条大多是 Synty 系（折扣券/唯一链接型资产）。
本轮那 2 条「1 → 0」正是这个口径的产物 —— **所以我在过程里先说过「揭示 2 条」，那是错的，已纠正**：
从页面**新增的码是 0 条**。
建议（未实施）：要么给「已揭示但无码」一个独立状态（界面才能诚实显示），要么只在真拿到码时才置 `revealed`。

## 5. agent 行为（正面）

- 逐行核对后才点：「点前均核对了该行文案确为『显示您的…密钥』，每行只点一次」。
- 遇到耗尽就停手，不硬点余下几行：「按纪律**就此停下**：不再对剩余 5 行继续点击」。
- 遇到不确定的交人工：「本单的档位资产属于『唯一链接』型…代金券已过期，故本单在 Humble 页面上无密钥可揭示」。
- 未拿接口的码冒充页面结果：「未做/未编造：没有把优惠码当密钥明文写入」。
