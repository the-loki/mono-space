## 0. 结论先行

1. **接口解析字段名是对的**（这是本次最大的未知）。真实响应里 key 在 `tpkd_dict.all_tpks[]`、
   码字段是 `redeemed_key_val` —— 实证见 §2：**接口取到 77 条 key、77 条全带码**。
2. **页面优先生效**：库层 77 个 key、`api:` 前缀补充行 **0** 条、页面码指纹前后**一字未变**（§3）。
3. **没有静默失效**：合并报告带 `apiKeys` / `apiCoded` / `supplemented` 三个数字，
   所以「页面本来就没缺口」与「接口解析出空」在数据上分得开（§2 的动机）。
4. **同步管线的另一半没被动**：`runSync` 仍全程只发一次订单列表请求，逐单详情只在合并那一趟请求（§4）。
5. **接口补充的真实价值已定性**（§6）：接口持有该单**完整的 key 清单**，但对**未揭示**的 key
   它同样拿不到码（`apiCoded: 0`）——因此它的价值只在「**页面整段读漏**」时体现。
   这条正向路径**仍未在真数据上出现**。

## 1. 合并规则（连接键与优先级）

页面读来的 key 身份是**资产显示名 slug**，接口的身份是 **`machine_name#keyindex`** —— 两套对不上，
所以**连接键只能取兑换码**：

| 情况 | 结果 |
|---|---|
| 码相同 | 同一条 key，**页面赢**（接口不覆盖页面的码、也不重复建行） |
| 接口有、页面没有的码 | **补进来** |
| 页面有、接口没有 | **保留**（含未揭示无码的行） |
| 接口 key 没有码 | **不补**（唯一连接键缺失，不猜） |

补充行身份 `api:<machine_name>#<keyindex>`：前缀的 `:` 是页面 slug 永远造不出的字符 ⇒ 不会撞身份、且一眼可辨来源；
身份由接口字段推导 ⇒ 重读幂等。补充行 `platform` 留 null（`machine_name` 后缀是旧「引擎」语义，不拿它当平台）。

## 2. 真接口实证：字段名与数字

审计原文（`52YH6x4ubXAB5qwr`，77 个 Epic key 的单）：

```json
{"at":"2026-09-26T14:45:10.765Z","tool":"keys_ingest","keyIds":[],
 "detail":{"order":"52YH6x4ubXAB5qwr","keys":77,
           "merge":{"status":"merged","apiKeys":77,"apiCoded":77,"supplemented":0}}}
```

- `apiKeys: 77` —— 详情端点**真取到了 77 条 key**（不是空响应、不是解析成 0 条）。
- `apiCoded: 77` —— **每一条都带兑换码** ⇒ `redeemed_key_val` 就是码字段，解析正确。
- `supplemented: 0` —— 这 77 个码**全都已存在于页面那份**里（按码对上），所以没有可补的。
  这是**正常结果**，不是失效。

### 为什么报告必须带这三个数字

首轮真跑时报告只有 `{"status":"merged","supplemented":0}`，而 `supplemented: 0` 有**三种成因**：

1. 页面本来就没缺口（正常）——本单就是这个；
2. **接口返回空**（例如码字段名解析错 → 接口 key 全无码 → 按「没码不猜」全跳过）→ **静默失效**；
3. 接口挂了（`status: 'failed'`）。

只记 `supplemented` 等于**没有证据**。补上 `apiKeys` / `apiCoded` 后，第 2 种成因无处可藏
（实现见 `16e5734`）。

## 4. 降级与边界

- **顺序是硬要求**：`host.keysIngest` 里**页面那份先落库**，然后才 try 接口那一趟。
  接口失败只降级为 `{status:'failed', reason}`（写进审计、并作为工具返回值给 agent），**不抛**。
  连「建 store 会话」抛错也落在同一降级里。单元测试用真实客户端 + 假 http（HTTP 500）覆盖。
- **同步管线没变**：`src/main/sync/sync.ts` 里 `fetchOrder` / `all_tpkds` 出现次数均为 **0**；
  `sync.test.ts` 的「全程只有一次订单列表 GET」断言未改动即通过。
- **没新增 agent 工具**：合并是应用侧的确定性逻辑，交给模型只会引入不确定性，且「页面优先」就不再由应用保证。

## 5. 已知代价（不是 bug，是这条决策的必然结果）

连接键**只有码**，因此「页面把某条 key 读成**未揭示（无码）**、而接口带了码」时，
接口那个码会被当作「接口独有」**另起一行补进来**，与页面那条**并存**——即使它们是同一条 key。
消除它只能放宽连接键（例如用资产名做弱匹配），代价是可能猜错，**属另一条决策**。

另：码不一致时我们**选页面**，因此可能记录到与接口不一致的值。

**实测修正（见 §6.3）**：这个「并存」要求「页面读到未揭示、而接口却带码」——
而 90 行全未揭示的那单实测表明**未揭示时接口同样没有码**，所以这个组合**在真实数据里不会发生**。
风险比当初估计的低得多；但它仍然是「连接键只有码」这一约束的理论后果，故保留记录。

## 6. 接口补充的真实价值（已定性）

四趟实测，把「补缺口」到底能不能补、能补什么，钉成了事实。

### 6.1 已揭示的单：接口有码，但页面也全有

`52YH6x4ubXAB5qwr`：`apiKeys: 77, apiCoded: 77, supplemented: 0`。
接口拿到 77 条、全带码，而页面 77 条也都带码 ⇒ 没有可补的。

### 6.2 没有 key 的单：接口也没有

`NeqxC3SrB5ZPtCnU`（音乐包，页面 0 行）：`apiKeys: 0, apiCoded: 0`。
⇒ 该单在接口侧本来就没有 key（下载型），不是解析失败（同一解析在上一单取到了 77/77）。

### 6.3 全部未揭示的单：接口有清单、但**同样没有码**（关键）

`TfCt8vyzpzeG3VPP`（90 行**全部**未揭示）：

```json
{"order":"TfCt8vyzpzeG3VPP","keys":90,
 "merge":{"status":"merged","apiKeys":90,"apiCoded":0,"supplemented":0}}
```

- `apiKeys: 90` —— 接口**返回了全部 90 条 tpkd**，与页面 90 行**一一对应**；
- `apiCoded: 0` —— 但**一条码都没有**：**未揭示的 key，接口的 `redeemed_key_val` 同样是空的**。

⇒ **对「未揭示」这类缺口，接口补充毫无价值**（同一份 tpkd 数据，码在两边都还没生成）。
这一点在实现时只是推理，现在是实测。

### 6.4 由此得出的价值边界

两次实测里 `apiKeys` 都**恰好等于页面行数**（77/77、90/90）——说明**接口持有该单完整的 key 清单**。
所以接口补充真正有用的场景只有一个：**页面整段读漏**（例如长时间扫描里 agent 中途失败，
只读到一部分甚至一行没读）。此时接口仍能给出完整清单（已揭示的连码一起），把漏掉的行补回来
——而且因为「同码页面赢」，已读到的那些不会被接口改写。

### 6.5 仍未观测到

1. **正向补充（`supplemented > 0`）**：四趟都没有出现，只有单元测试（mock）覆盖。
   要观测到，需要一个「页面读漏而接口有」的真实实例。
2. **补充行的平台留 null 在界面上的呈现**（真接口下从未产生补充行）。
3. **「未揭示的页面行 + 接口带码」并存**（§5 的已知代价）：6.3 表明这种组合**在真实数据里不会发生**
   —— 因为未揭示时接口也没有码。
