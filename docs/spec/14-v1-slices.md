## 1. 做到哪算够：v1 的终点

**v1 = 端到端手动跑通「同步 → 揭示 → 兑换」，单条、串行、人在环路；台账可读；AppImage 可分发。**
**不含内置代理（脚本自动修复）。**

理由：本应用的核心价值就是把「还没揭示的 Key 揭示出来、把兑换码兑换进 Fab」。只做一半（只揭示不兑换）不解决用户的问题。**内置代理是韧性特性（页面改版时自动修脚本），不是核心链路**，推迟到 v1.1 不影响核心价值成立。

## 3. 实现顺序与依赖

```
S0  1. 脚手架（electron-vite 5 + Vite 7.3.6 + Electron 44.4.5）
        └─ ESM main + `.cjs` sandboxed preload；pnpm 10；AppImage；模板预置 homepage/author/desktopName
    2. 数据层（SQLite：订单→包→key 三层 + 订单快照；key 双状态字段；账号维度预留）
    3. Humble 只读同步（GET /api/v1/user/order；定期全量比对；分页）
    4. 台账 UI（虚拟滚动、筛选、状态列）
S1  5. 自动化骨架：store session 工厂（client hints 注入，ADR-0002）+ 可见窗口 + MV3 扩展装载/热替换骨架
    6. 揭示流程（Humble，单条）+ 人在环路暂停点 UI + 台账回写
S2  7. 兑换流程（Epic 账号页，单条；按 #12 状态机与错误码映射）
    8. My Library 归属校验
S3  9. 内置代理（离线写/修扩展）+ 工具契约落地 + 多选排队
```

**关键依赖**：
- 3 依赖 2；5 依赖 1；6 依赖 3+5；7 依赖 5（+`#12` 已决策）；9 依赖 5+7（页面结构必须先真实存在）。
- **5（自动化骨架）必须在 6/7 之前**，且必须先把 **client hints 注入**做进 session 工厂——否则揭示/兑换页直接 403（ADR-0002）。

**每步 DoD（完成判据）**
1. `pnpm build:linux` 出 AppImage 并能启动（Ubuntu 24+ 自动 `--no-sandbox`）。
2. 三层表 + 账号字段 + 可导出 CSV/JSON；迁移脚本。
3. 真实库（2000+ key）增量同步一次，耗时与内存可接受。
4. 列表流畅（虚拟滚动），2000+ 条不卡。
5. 可见窗口打开 fab/epicgames 稳定 200（未登录）；扩展能装载、能热替换。
6. 单条揭示端到端成功，台账状态正确流转（含 `needs_human` 暂停与恢复）。
7. 单条兑换端到端成功，My Library 校验通过，错误码正确归类。
8. 校验失败能正确落 `needs_human`。

## 4. 必备 vs 可推迟

**「没它就不算 v1」**
- 脚手架 + AppImage 分发（Linux）。
- 数据层 + Humble 只读同步 + 台账可读（2000+ 规模）。
- 揭示（单条）、兑换（单条）、人在环路暂停点 UI。
- store session 的 client hints 注入（否则功能不可用）。
- 日志脱敏 + 零遥测（`#10`）。

**可推迟（v1 之后）**
- 内置代理 / 脚本自动修复（→ v1.1）。
- 多选排队（→ v1.1；**批量并发永不做**）。
- 首次运行引导的精打磨（骨架已定：「登录 → 首次同步 → 主界面」）。
- 代理快照与扩展版本的保留策略（留多久/清理）。
- 大库性能参数微调（**必须先拿真实 2000+ 数据量测过**再定）。
- 应用图标等标识细节。
- deb/rpm 分发（AppImage 为主；deb 需 `homepage`，见 `#17`）。
- Wayland/X11 下可见窗口与接管的细节打磨。

---

## 5. 2000+ key 规模下的「可用」

- **增量同步**：定期**全量拉订单列表比对**（`#8`/`#11`），只写变化；不每次重建。
- **分页 + 虚拟滚动**：台账列表按窗口渲染，不把全量塞进一次渲染。
- **状态列直接可见**：揭示状态 / 兑换状态两列（两字段独立，`#8`），支持筛选「未揭示」「已揭示未兑换」。
- **不预加载兑换码明文**：列表只显示状态，码按需读取（减少明文外泄面）。

---

## 6. 批量操作的取舍

- **v1：只做单个**（手动逐条）。这是「半自动优先 + 人类节奏」的直接体现，也把不可逆操作的风险压到最小。
- **v1.1：多选排队**——多选只是**入队**，执行仍**串行单条**、仍走预检 + 单条试探、仍按人类节奏节流。
- **永久不做：批量并发**（与 Humble `robots.txt`/ToS、Epic 风控冲突，`#18` §4）。

## 7. v1 验收清单（含 HITL 残差回填）

- [ ] AppImage 在目标 Linux 上装完即启动（Ubuntu 24+ 自动降级沙箱）。
- [ ] 首次运行引导跑通：登录 Humble / Epic → 首次同步 → 主界面。
- [ ] **首次登录 checklist（回填 `#16`/`#18`/`#12` 的 HITL 残差）**：
  - [ ] Fab profile → Redeem Code 的确切 href。
  - [ ] Epic 账号兑换页实际渲染文案 vs `#18` 错误码的对照。
  - [ ] 登录态下 `/i/users/me` 返回 200、一次真实 claim 全程无 challenge。
  - [ ] Epic 2FA 的实际方法与「约 30 天重索」的实测。
- [ ] 单条揭示端到端成功；单条兑换端到端成功（My Library 校验通过）。
- [ ] 未知错误码 → `needs_human`；会话失效 → 中止整批、重登重跑。
- [ ] 日志无明文凭据/key（脱敏）；无遥测出网。
